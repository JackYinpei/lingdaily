# Agent 开发协作与架构决策

状态：建议工作方式。本轮没有启动多个 Agent，也没有引入运行时 Agent 框架。

## 先把几个概念说清楚

| 名称 | 实际含义 | 本项目如何用 |
| --- | --- | --- |
| 分层 | 给界面、业务状态、外部服务规定职责 | 用少量边界隔离音频和网络，方便定位问题 |
| MVVM | View 显示；ViewModel 管理可显示状态和用户操作 | 适合 SwiftUI 页面；复杂音频另有服务 |
| Repository | 向页面提供数据，隐藏网络与本地存储细节 | 历史和待同步数据需要；简单页面按需使用 |
| Clean Architecture | 让核心规则尽量少依赖框架 | 借用依赖方向，不强制建立很多空层 |
| TCA / Redux | 以统一的动作和状态更新方式管理复杂交互 | 先用普通状态机；实际需要再引入框架 |
| ADR | 一页记录“为什么做这个技术选择” | 影响身份、协议、数据或依赖的决定需要记录 |
| Spec 驱动 | 先写用户行为、输入输出和完成条件 | 本项目默认流程 |
| 多 Agent | 多个开发者式角色分工，可以并行也可以串行 | 任务独立且明确安排时才使用 |
| 产品中的 AI Agent | 模型根据上下文调用工具完成业务动作 | 当前 Live 导师只需受限工具，不需要自动多角色讨论 |

层数和 Agent 数量都不能代替验收。适合当前项目的做法是：一个清楚的任务、稳定的数据约定、一组可复现的完成证据。

## 默认流程

1. 读根 `AGENTS.md` 和本功能相关文档，标明当前现状、目标和兼容规则。
2. 复制 [任务模板](templates/agent-task.md)，写出一个可独立验收的结果。
3. 先确定页面状态和接口样例。契约有变化，更新 [数据文档](04-data-contracts.md) 和对应 fixtures。
4. 完成一条纵向用户流程；只重构这条路径真正需要的代码。
5. 验证正常、失败、取消、重复和账号变化；证据写回任务。
6. 对照 diff 复核授权、数据、iOS 15 和文档；提交一个容易审查的变更。

同一个 Agent 可以顺序完成研究、实现和复核这些角色。复核阶段要回到原始验收条件，不能只复述实现者给出的结论。

## 什么时候才适合并行

例如组件 Gallery、已有 API 的合成样例整理、独立文案检查可以在接口定好后分工。语音状态机、同一个 pbxproj、同一迁移文件或同一个契约不适合多人同时自由修改。

如果任务发起者明确安排并行，每项任务需要独立文件范围、输入/输出、责任人和验收条件；使用独立分支/工作区减少文件竞争。一个集成责任人管理公共契约和合并顺序。工具读取、测试并行不等于一定要启动多个 Agent。

## Agent 需要遵守的项目约束

| 场景 | 具体约定 |
| --- | --- |
| 新界面 | 引用已有 Token 和页面模板；状态齐全；中文/英文/日文有回退 |
| 新依赖 | 写明用途、iOS 15 与传递依赖兼容性、锁定版本、替代方案 |
| 新接口 | 确定身份、响应、错误、分页、重试与兼容；不能先编造 URL 写进客户端 |
| 数据写入 | 使用当前 owner；保存确认与工具 accepted 分开；重复提交有定义 |
| 日志和测试 | 用合成数据；不读取或输出 `.env` 中的真实密钥 |
| 生产数据 | 遵守根 AGENTS 的 preflight/migration/postflight 规则 |
| 完成声明 | 区分编译通过、模拟器运行、真机音频、生产联调；未执行的检查明确标记 |
| 产品新创意 | 用户选定后再进排期；不把创意稿当成已确认需求 |

仓库文件放长期规则，单次任务文件放本次目标，工具输出放验证证据。不要把整个聊天记录或不断增长的“记忆”当成系统设计。

## 建议建立的决策记录

下表是决策索引，技术建议尚不代表用户已批准全部细节；进入相应阶段时填写 [ADR 模板](templates/adr.md)。

| 编号 | 题目 | 本次建议 | 重新评估条件 |
| --- | --- | --- | --- |
| ADR-001 | 原生路线与最低系统 | SwiftUI + iOS 15；最低系统已确定 | 明确加入近期 Android 目标或用户修改最低版本 |
| ADR-002 | 服务端复用与移动身份 | Next.js 公共业务服务；Cookie/Bearer 身份适配 | 旧 OAuth 无法安全映射或独立后端确有部署需求 |
| ADR-003 | 状态和依赖边界 | 按 Feature 组织；显式注入；音频状态机 | 状态组合和团队规模带来可证明的维护问题 |
| ADR-004 | 历史的主题与语言身份 | 保留主题唯一键，新消息记录语言/练习尝试 | 决定推出独立分语言会话、故事分支或多次练习统计 |
| ADR-005 | Live 协议和模型 | P0 验证后固定组合，服务端可配置 | 官方停用、延迟/成本不合格或地区不可用 |
| ADR-006 | 本地存储 | Keychain + 有版本文件；需要复杂查询时再评估数据库 | 草稿规模、离线检索或多实体事务成为实际需求 |

## 一个合适的下一步任务

“验证现有历史详情 API 在保留 Web Cookie 行为的前提下支持移动用户身份。”交付应包括认证方案、合成用户 A/B、有效与伪造 Token 测试、跨用户隔离测试和 iOS 请求样例。若当前仍处于文档阶段，则交付该任务的规格与风险清单，不提前修改服务端。

这样的任务比“实现整个 iOS 架构”更容易判断是否完成，也能尽早暴露最重要的兼容问题。
